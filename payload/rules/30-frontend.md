# 前端规则

## 实现原则
- 优先遵循既有框架、目录、组件和状态管理方式。
- 不新增依赖，除非用户明确批准。
- 页面逻辑、接口调用、状态管理和视图组件应保持清晰边界。
- 请求和响应必须遵循 API 契约。
- 不直接信任前端校验，后端仍需校验。

## 代码质量和封装
- 组件、变量、函数、composable、store、API 方法命名必须表达业务含义，禁止无上下文的 `data`、`list`、`info`、`handleClick`、`submit`、`temp`。
- 页面组件负责流程编排和视图组合；可复用 UI、业务表单、查询条件、表格列配置、接口调用和状态逻辑应按既有目录拆分。
- 接口请求必须集中在 API 层或既有 request 封装中，禁止在组件里散落拼接 URL、重复处理 token、错误码或分页结构。
- 表单模型、查询模型、接口 DTO、展示 VO 必须边界清晰；不要直接把后端原始对象到处透传。
- 重复交互逻辑应提取为组件、composable/hook、store action 或局部工具函数，但必须有真实复用点和清晰输入输出。
- 复杂条件、权限判断、按钮可见性、状态文案和颜色映射应集中定义或提取为有语义的方法，禁止在模板中堆叠复杂表达式。
- 状态管理只存跨组件、跨页面或需要缓存的状态；局部表单和弹窗状态优先留在组件内。
- 组件 props、emits、slots 必须命名清晰，避免通过隐式全局变量或深层对象突变传递状态。
- 列表页、详情页、表单页和弹窗必须有稳定的数据流：初始化、加载、成功、失败、重置、销毁边界清楚。
- 前端长整型 ID 必须按字符串处理，禁止转 Number；展示、提交和路由参数保持一致。

## 必须覆盖
- 加载态
- 空态
- 错误态
- 成功反馈
- 权限不足
- 表单校验
- 分页和筛选
- 重复提交防护

## 表单校验
- 提交表单必须实现前端校验，并与后端验证层和 API 契约保持一致。
- 后端 DTO、Request、Form、Validator 或注解中必填的字段，前端也必须必填并阻止提交。
- 输入长度必须参考数据库字段长度、后端验证注解和 API 契约；前端最大长度不得大于后端或数据库允许长度。
- 必须覆盖最大长度、最小长度、必填、格式、枚举、数值范围、数组数量和高风险字段确认等规则。
- 如果数据库字段、后端验证层和 API 契约约束不一致，必须停止并询问，不得自行猜测。
- 前端校验只做提前反馈，不能替代后端校验；后端仍必须完整校验。
- 校验提示必须使用简体中文，说明错误原因和修正方式。
- 新增或修改表单时，交付说明必须列出每个提交字段的校验来源。

## 验证
前端变更应尽量运行：
- 类型检查
- lint
- 单元测试
- 组件测试
- e2e 或手动关键路径验证
- 多视口截图检查，如涉及视觉

## 禁止事项
- 禁止在页面组件中堆叠大段业务逻辑、接口细节和数据转换。
- 禁止复制粘贴相似表单、表格、弹窗逻辑而不评估复用。
- 禁止为了抽象制造难以理解的万能组件或配置黑盒。
- 禁止直接修改 API 返回对象导致状态来源不清。
- 禁止把权限、状态映射、枚举文案散落在多个页面中。
- 禁止提交表单只做 UI 必填标记但没有实际校验规则。
- 禁止前端表单长度、必填、枚举或格式校验与后端验证层不一致。
