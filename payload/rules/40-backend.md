# 后端规则

## 分层原则
- Controller 只负责接收请求、基础校验、调用 Service、返回统一响应。
- Service/ServiceImpl 负责业务校验、权限、状态流、事务、缓存协调和通知触发。
- Mapper 只定义持久化方法。
- XML 写显式 SQL。

## 禁止调用流
```text
Controller -> Mapper
Mapper -> Service
Controller -> Controller
Entity -> Service
```

## 必须考虑
- 事务边界
- 权限校验
- 租户隔离
- 软删除
- 幂等性
- 重复提交
- 审计日志
- 异常处理
- 数据兼容
- 对外 ID 字符串和前端长整型精度

## 生产级手写要求
- 编码前必须先读同模块或相邻模块的 Controller、Service、Mapper/XML、DTO、VO、Entity 和测试。
- 不清楚字段、状态、权限、租户、删除、响应格式或错误码时停止询问。
- 复用既有项目抽象，禁止新造一套响应、分页、异常、权限或租户模型。
- 新增公共方法或抽象前，必须确认至少两个真实调用点或明确变化隔离价值。
- 对外 API 的请求/响应对象必须稳定，避免直接暴露数据库结构。
- Create/Update 请求 DTO 必须声明必填、长度、格式、枚举、数值范围和数组数量等验证规则，并与数据库字段长度、OpenSpec/API 契约和前端表单校验保持一致。
- 数据库可以保留 `pk_id`，但对外 API 必须使用 `id`，前端按字符串处理。
- 后端内部把 API 字符串 `id` 校验后再转换为 `Long`，非法 ID 返回参数错误。
- 查不到数据时返回业务不存在，不允许抛成 500。
- 删除、状态变更、扣减、发布、回滚等高风险动作必须有幂等、审计和确认策略。
- 实现必须有验证证据；无法自动测试时说明手动验证路径和残余风险。

## 代码质量和封装
- 类、方法和变量命名必须表达业务含义，禁止 `handle`、`process`、`doSomething`、`data`、`item`、`temp` 等无上下文命名。
- 方法职责必须单一；复杂业务流程应拆为可命名的私有方法或领域步骤，禁止一个方法混合参数校验、权限、查询、状态流转、组装和副作用。
- 公共抽象只承载稳定规则；不要为了“看起来高级”提前抽象，也不要把不同业务强行塞进一个通用方法。
- 重复代码优先提取到本模块内的私有方法、领域服务或既有工具；跨模块复用前必须确认边界稳定。
- DTO、VO、Command、Query、Entity 不能混用；入参、出参、持久化对象和内部业务对象必须边界清晰。
- 状态、类型、来源、动作等业务枚举必须使用明确命名和集中定义，禁止魔法字符串、魔法数字散落在业务代码中。
- 分支逻辑必须体现业务规则；复杂条件应提取为有业务语义的方法，禁止堆叠难以审查的长 boolean 表达式。
- 异常信息、日志和审计字段必须能帮助定位业务动作，不输出敏感信息，不吞掉根因。
- 查询组装、对象转换和响应组装应有清晰位置，避免 Controller、Service、Mapper/XML 互相污染职责。
- 高复用代码必须有低耦合接口和明确输入输出，禁止依赖隐式全局状态或隐藏副作用。

## 禁止事项
- 禁止 Controller 写业务逻辑。
- 禁止 Service 拼接 SQL 字符串。
- 禁止静默吞异常。
- 禁止伪实现。
- 禁止无关重构。
- 禁止低质量模板拼接式 CRUD。
- 禁止空方法、只有 TODO 的方法或没有业务含义的“高级抽象”。
- 禁止为复用牺牲业务语义，把不同规则合并成难以审查的万能方法。
- 禁止把命名、分层和封装问题留给后续重构，除非用户明确批准分阶段处理并记录风险。
